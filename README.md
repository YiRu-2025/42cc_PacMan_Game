# Pac-Man

## Description

A Pac-Man game in Python and pygame, played on mazes produced by another
team's A-Maze-ing package rather than on a hand-drawn board.

The player moves through a maze eating pacgums while four ghosts chase
them. Eating a super-pacgum turns the ghosts frightened for a few seconds,
during which the player can eat them for points. Clearing every pickup
advances to the next maze; the run ends when the lives run out, the level
timer expires, or the last level is cleared.

Two things make this more than a clone. The maze is generated by a
third-party package we do not control, so the game has to adapt to
whatever grid it is handed — including the sealed "42" pattern the
generator stamps into the middle of every maze, which nothing can enter.
And every number that defines a run comes from a JSON configuration file
that is replaced at review time, so no size, score or level count may be
assumed anywhere in the code.

## Instructions

### Requirements

Python 3.10 or newer. Everything else is installed by `make install`.

### Install and run

```sh
python3 -m venv .venv
source .venv/bin/activate
make install
make run
```

`make install` installs the dependencies in `requirements.txt` and then
the assigned maze package from the wheel committed in `vendor/`. The wheel
is in the repository on purpose, so the exact version this game was built
against is reinstalled rather than fetched.

To run with a different configuration file:

```sh
make run CONFIG=other.json
# or
python3 pac-man.py other.json
```

### Menus

The game opens on the main menu. Arrow keys move the cursor, Enter or
Space chooses, Escape goes back.

| Entry | What it does |
| --- | --- |
| **Start** | Begins a new run at level 1 |
| **Highscores** | The top ten table; any key returns |
| **Instructions** | Controls, scoring and cheat keys, read from the live configuration so the numbers shown are the ones in play |
| **Quit** | Closes the game |

Escape on the main menu quits, the same as choosing Quit.

The main menu shows the best score on record underneath the entries, or
nothing at all when the table is empty.

### Playing

| Key | What it does |
| --- | --- |
| Arrow keys, or W A S D | **Hold** to keep moving in that direction; **tap** to move exactly one cell. Releasing the key stops the player. If two keys are held, the most recent one wins |
| Escape | Pause (held keys are forgotten, so nothing runs away on resume) |

The player never moves by itself. A blocked direction simply leaves it
where it is, still facing that way.

### Pause

Escape raises a pause overlay over the frozen game. The game underneath
receives no updates while it is covered, and is still drawn, so it is
clear what is being returned to.

| Entry | What it does |
| --- | --- |
| **Resume** | Back to the game, unchanged |
| **Main menu** | Abandons the run and returns to the menu |

Escape resumes, which is what pressing it a second time should mean. An
abandoned run records no score, because the subject asks for a name only
when a game is won or lost.

### Cheat keys

Available during play. They exist so that a reviewer can see all ten
levels, the victory screen and the frightened state without having to
play well.

| Key | What it does |
| --- | --- |
| `1` | Skip to the next level |
| `2` | Toggle invincibility |
| `3` | Freeze the ghosts |
| `4` | Grant an extra life |
| `5` | Toggle double speed |

`1` is the most useful one: holding it down walks through every level to
the victory screen in a few seconds.

The Instructions screen reads `constants.CHEAT_BINDINGS`; the game reads
`cheat.CHEAT_ACTIONS`. They are two tables, and `tests/cheat_test.py`
fails if their keys ever differ.

### End of a run

A run ends when the lives reach zero, the level timer expires, or the last
level is cleared. The result screen shows the verdict, the score, the
level reached, and whether the score makes the top ten. Type a name and
press Enter to save it, or Escape to skip. The highscore table follows,
with the new row picked out.

Only letters, digits and spaces are accepted, up to ten characters.
Anything else is ignored as it is typed, so the field never shows a
character that would later be dropped.

## Configuration

The game reads one JSON file, named on the command line. Blank lines and
lines whose first non-blank character is `#` or `//` are stripped before
parsing. Comments after a value on the same line are not supported.

```json
# ---- Game ----
{
  "highscore_filename": "highscore.json",
  "lives": 3,
  "seed": 42,
  "level_max_time": 90,

  # ---- Scoring ----
  "points_per_pacgum": 10,
  "points_per_super_pacgum": 50,
  "points_per_ghost": 200,

  # ---- Collectibles ----
  "pacgum": 42,

  # ---- Levels (array, one object per level) ----
  "levels": [
    { "width": 20, "height": 15 },
    { "width": 25, "height": 18 }
  ]
}
```

| Key | Default | Accepted | Meaning |
| --- | --- | --- | --- |
| `highscore_filename` | `highscore.json` | non-empty string | Where the top ten is stored |
| `lives` | 3 | 1 – 99 | Lives at the start of a run |
| `seed` | 42 | 1 – 2³²−1 | Seed for the first maze |
| `level_max_time` | 90 | 1 – 3600 | Seconds allowed per level |
| `pacgum` | 42 | 1 – 10000 | Pacgums placed on each maze |
| `points_per_pacgum` | 10 | 0 – 10000 | Score for one pacgum |
| `points_per_super_pacgum` | 50 | 0 – 10000 | Score for one super-pacgum |
| `points_per_ghost` | 200 | 0 – 10000 | Score for eating a frightened ghost |
| `levels` | 10 mazes, 15×11 growing to 24×15 | 5 – 200 per side | One object per level |

### What happens to a bad file

Nothing in this file can stop the game from starting. The parser reports
each problem in one readable line on stderr and carries on with a value
that works:

- **File missing, unreadable, or not UTF-8** — every default is used.
- **Not valid JSON, or not a JSON object** — every default is used.
- **A key is missing** — that one default is used, silently, because an
  absent key is a choice and not a mistake.
- **A value has the wrong type** — the default is used and the problem is
  reported. `true` is rejected where an integer is expected, because
  `bool` is a subclass of `int` in Python and would otherwise pass as 1.
- **A value is out of range** — the default is used and the problem is
  reported.
- **Unknown keys** — ignored, with a note, which catches typos.
- **`levels` is absent, empty, or not a list** — the default ten levels
  are used. An unusable entry inside the list is skipped.
- **Fewer than ten levels** — the list is padded to ten, because the
  subject requires at least ten.

The decision behind all of this: a configuration file is edited by a
person, and a game that refuses to start because one number is wrong is
less useful than one that says what it ignored and runs anyway.

## Highscore

The top ten scores are kept in the JSON file named by
`highscore_filename`, as a list of `{"name": ..., "score": ...}` objects.
The table is read once when the game starts and written when it exits or
when a new score is saved.

Rules:

- Ten entries at most, best first.
- A score qualifies when the table has room, or when it beats the lowest
  entry. **Equal scores do not displace an existing entry**, so whoever
  got there first keeps the higher row.
- Names are at most ten characters and may contain only letters, digits
  and spaces.
- Negative scores are clamped to zero.

### Why it was built this way

**JSON rather than a text format of our own.** The file is small, it is
already in the project for the configuration, and a reviewer can open it
and see what is in it. A custom format would need a parser and a test
suite of its own to earn nothing.

**Loading never raises.** A corrupt or hand-edited score file is treated
exactly like the configuration file: the problem is reported and the game
starts with an empty table. Losing a scoreboard must not cost someone
their game. Handled: the file is absent, unreadable, not UTF-8, not valid
JSON, not a list, holds rows that are not objects, rows missing a key,
rows with a name or a score of the wrong type, and more rows than the
limit.

**Saving is atomic.** The table is written to a temporary file beside the
target and then moved into place, so an interrupted save cannot leave a
half-written table behind. If the disk is full or the directory is
read-only, the failure is reported and the game carries on rather than
crashing at the very end of a run.

**An explicit character whitelist, not `str.isalnum()`.** That method
accepts accented letters and CJK characters, which the subject's
"alphanumeric" does not. Characters outside the whitelist are dropped as
they are typed rather than rejected, so a player who types an accent
simply sees nothing happen.

## Maze Generation

Mazes come from the assigned `mazegenerator` package, version 2.1.0,
installed from the wheel in `vendor/`.

The package is used through one adapter, `pacman/maze_loader.py`. Nothing
else in the game imports it, and nothing else knows how it encodes a maze.

### What the package gives us

`MazeGenerator(size=(width, height), perfect=False, seed=n)` exposes a
`maze` property: a list of rows of integers, indexed `maze[y][x]`. Each
integer is a bitmask of the walls around that cell — north 1, east 2,
south 4, west 8 — so a cell of 10 has walls to the west and east and is
open north and south.

Three properties of the package drive the adapter's design:

1. **`perfect=False` is required.** A perfect maze has exactly one route
   between any two cells, which means dead ends everywhere and a player
   who can be cornered with no escape. Braided mazes have loops, which is
   what Pac-Man needs.

2. **`size` is `(width, height)` but the grid is `maze[y][x]`.** The two
   are in opposite orders, and this is the single easiest thing to get
   wrong.

3. **The generator stamps a sealed "42" into the middle of every maze
   that is large enough.** Those cells have all four walls up and nothing
   can enter them. A level that placed a pacgum there could never be
   cleared, so the adapter runs a breadth-first search from the maze entry
   and exposes the set of cells that are actually reachable. Everything
   above it works from that set, never from the raw dimensions.

### What the adapter exposes

A frozen `Grid` dataclass, which speaks in `Direction` rather than in bit
values:

- `is_open(x, y, direction)` — can a mover leave this cell that way
- `neighbours(x, y)` — every reachable adjacent cell, in a fixed order
- `walls_at(x, y)` — the blocked sides, for the renderer
- `walkable` — every cell reachable from the entry
- `centre()`, `corners()` — spawn points, snapped to the nearest walkable
  cell, because the geometric centre and the corners can fall inside the
  sealed pattern
- `nearest_walkable(x, y)` — the snapping itself, with ties broken by
  coordinate so that one maze always lays out the same way

Every call into the package is wrapped, and every failure — a missing
package, a generator that raises, a malformed grid, a maze with no usable
corridors — surfaces as one `MazeError`. The application catches it and
shows a message; no traceback reaches the player.

### Seeds

Level 1 is generated with the seed from the configuration, so the first
maze is the same every run and a reviewer can compare two runs. Every
later level asks for seed 0, which is how this package is told to pick its
own. A loader is fixed to one size, so one is built per level.

## Implementation

### Language and library

Python 3.10+ and pygame. The subject allows only pygame calls that have an
MLX counterpart, so the whole of pygame is confined to one module,
`pacman/gfx/gfx.py`, whose docstring carries the mapping call by call. Two
consequences are visible throughout the game:

- **No `pygame.draw.*`.** Filled shapes come from an offscreen surface
  that is filled once and blitted, which is what `mlx_new_image` plus
  `mlx_put_image_to_window` does.
- **No `pygame.transform.*`.** Scaling and quarter turns are written out
  as loops over `get_at` and `set_at`, once per sprite at load time, and
  cached. This is what lets three eastward player frames serve all four
  facings: the other three are derived by turning or mirroring pixels.

`pygame.init()` is never called either, because it would start
`pygame.mixer`, which the subject forbids. Only display and font are
initialised.

### Movement

Entities move cell by cell. Each carries a cooldown and takes one step
every `1 / speed` seconds, so speed is in cells per second and independent
of the frame rate. Frames longer than `MAX_FRAME_DT` are capped.

The player is driven by input only. `Player` keeps the list of held
direction keys (the most recent wins) and the last press as a one-shot
tap, so a key released between two steps still moves one cell. With no key
held and no tap pending the player does not move, and its cooldown is
reset so the next press responds immediately. Held keys survive a respawn
and a level change; the play scene clears them on pause.

### Ghosts
Each ghost is a three-state machine: chasing, frightened, dead.
One breadth-first search per frame from the player's cell is shared by all
four ghosts. A chasing ghost steps to the neighbour with the smallest
distance, a frightened one to the largest; ties go to the first neighbour
in north, east, south, west order, so behaviour is deterministic.

A frightened ghost moves at `FRIGHTENED_SPEED_FACTOR` of its normal speed.
An eaten ghost is moved at once to its home cell (the free cell beside its
corner, not the corner itself), stays there for `GHOST_RESPAWN_DELAY`, then
chases again. Each ghost's home is also its starting cell.

Contact is the same cell, or a swap of cells during the last step.

### Timings

| Constant | Value | Meaning |
| --- | --- | --- |
| `FPS` | 60 | Frame rate cap |
| `PLAYER_STEPS_PER_SECOND` | 6.0 | Player speed, in cells |
| `GHOST_STEPS_PER_SECOND` | 5.0 | Ghost speed, in cells |
| `FRIGHTENED_DURATION` | 7.0 s | How long a super-pacgum lasts |
| `FRIGHTENED_SPEED_FACTOR` | 0.6 | Frightened ghosts are slower |
| `GHOST_RESPAWN_DELAY` | 5.0 s | Before an eaten ghost chases again |
| `DEATH_PAUSE` | 1.5 s | The world freezes after a death |
| `RESPAWN_GRACE` | 1.5 s | Invulnerability after respawning |
| `MAX_FRAME_DT` | 0.1 s | Longest step the simulation accepts |

`RESPAWN_GRACE` exists because without it a ghost standing on the spawn
point takes every remaining life in a row.

### Design decisions worth stating

**A timeout ends the run, it does not cost a life.** When the level timer
reaches zero the lives drop to zero and the run is lost, so the score is
saved like any other game over. The alternative — losing one life and
restarting the timer — makes the timer almost free and removes the
pressure it exists to create.

**The score never decreases.** Nothing in the game subtracts points; the
method that adds them asserts it.

**Score and lives carry across levels.** A new level rebuilds the maze,
the pickups and the timer, and leaves the run's own state alone.

**Artwork is optional.** Every drawable thing has a sprite path and a
fallback colour. The renderer tries the file and fills a flat colour when
it is not there, so the game is playable and legible with an empty
`assets/` directory and improves one file at a time. The same applies to
fonts: the title face ships with the game, the body face is whichever
monospace the system offers, and pygame's built-in font catches the rest.

**Monospace for the HUD is functional.** The score and the countdown
change every frame, and in a proportional face the digits have different
widths, so right-aligned text shifts a few pixels each second.

**The window is sized once.** It is sized for the largest level in the
configuration before any scene exists, and smaller mazes are centred
inside it, so the window never changes size mid-game. The cell size is
computed from the maze and the screen rather than fixed, because the
configuration can ask for a maze no screen could show at a readable size.

## General Software Architecture

The package is split into layers. A layer may import from the layers below
it and never from the ones above, which is what keeps the rules testable
without a window and the drawing testable without a game.

```
pac-man.py                 argument checking only
└── pacman/app.py          wiring and the frame loop
    ├── pacman/scenes/     one screen each
    ├── pacman/game.py     the rules
    │   ├── level.py       pickups and spawn points
    │   └── entities/      player and ghosts
    ├── pacman/gfx/        drawing; the only pygame in the project
    ├── pacman/config.py   ─┐
    ├── pacman/highscores.py├ the edges: files and the third-party package
    ├── pacman/maze_loader.py┘
    └── pacman/constants.py values with no dependencies
```

### `app.py` — wiring and the loop

The only module that knows the whole program. It reads the configuration,
opens the window, loads the highscore table, and runs a stack of scenes
until it empties.

It is also the only place where the menu and the gameplay meet. The menu
is handed a callable that builds a game; a finished game answers with a
`Finish` transition that the application turns into the name prompt.
Neither imports the other.

### `scenes/` — the screens

`MainMenuScene`, `PlayScene`, `PauseScene`, `ScoresScene`,
`InstructionsScene`, `NameEntryScene`, `MessageScene`, over the `Scene`
interface in `scenes/base.py`.

A scene answers an event or a tick with a `Transition` — `Push`,
`Replace`, `Pop`, `Finish`, `Quit` — or with `None` to stay put. It never
drives the window and never calls another scene.

Screens are kept on a **stack** rather than in a single slot. That is what
lets the pause overlay sit on top of a running game and leave it untouched
underneath: a scene marked transparent is drawn over the one below, and
only the top of the stack receives input and updates.

`Finish` exists because the obvious mistake is to push the result screen
on top of the finished game, which then reappears when the result is
dismissed. The transition replaces the gameplay scene instead, so that
mistake is not available.

### `game.py`, `level.py`, `entities/` — the rules

Movement, pickups, ghost behaviour, scoring, lives and level flow. No
pygame, no drawing, no files. State is layered by lifetime, which is what
makes the carry-over rules fall out naturally:

- the whole run — score, lives, level index, phase
- one level — the maze, the pickups, the timer
- one life — the player, the ghosts, grace and stun

`cheat.py` sits here too, as state the gameplay reads rather than
shortcuts bolted onto the input handler.

### `gfx/` — drawing

`gfx/gfx.py` owns the window and the input queue and is the single module
that touches pygame. `gfx/renderer.py` turns grid coordinates into pixels
and chooses a sprite or a fallback colour. It reads game state and never
writes it, through four read-only protocols that declare exactly what it
needs — which is also what lets it be tested with hand-built fakes.

### The edges

`config.py`, `highscores.py` and `maze_loader.py` each absorb bad input
and report it in one readable line, so nothing above them has to cope with
a malformed file, a missing key or a failed import.

### `constants.py`

Directions, timing, layout, and the sprite-path and fallback-colour
tables. Anything the configuration file can set lives in `config.py`;
anything it cannot lives here. A value kept in both would eventually
disagree with itself.

### Level layout (`level.py`)
Pacgums cover every walkable cell except the four corners (super-pacgums)
and the player's start. Ghosts start beside the corners. The player starts
on the walkable cell nearest the geometric centre. The sealed "42" cells
are never walkable, so a level can always be cleared.
`MazeLoader.__init__` builds the generator, which already generates one
maze with seed 1; `generate(seed)` then replaces it.

## Packaging

`make package` runs PyInstaller on `pacman.spec` and zips the result.

- **Read-only files** (`assets/`, the default `config.json`, `README.md`)
  are bundled and found through `constants.resource_path`, which uses
  `sys._MEIPASS` when frozen and the repository root otherwise.
- **Written files** (the highscore table) go through `constants.data_path`:
  beside the executable, or `~/.pac-man` if that directory is not
  writable. Never `_MEIPASS`, which is deleted on exit.
- **Configuration**: with no argument the executable uses a `config.json`
  beside it if present, otherwise the bundled default.
- **Release**: upload the zip to itch.io (`make itch ITCH=user/game`) and
  set the page to non-public in the dashboard.
- PyInstaller cannot cross-compile; build on each target platform.
- If `pip install pygame` compiles from source and takes minutes, the
  Python version has no prebuilt wheel. Use Python 3.12 or 3.13.

### How AI was used

AI assistance was used throughout this activity. Being specific
about it matters, because the subject requires that we understand and can
explain everything we submit.

**Where it was used heavily**

- The graphics layer (`gfx/gfx.py`, `gfx/renderer.py`): the MLX-equivalent

  transform, and the sprite fallback mechanism.
- The scene framework (`scenes/base.py`, `app.py`) and most of the menu
  screens.
- `maze_loader.py` and `highscores.py` in their first versions, later
  rewritten and improved by us — the deterministic tie-break in
  `nearest_walkable` and the `walls_at` method are ours.
- Placeholder sprites in `assets/`, produced by a script.
- Reviewing our code: several real defects were found this way, including
  an off-by-one in the entity step loop, an indentation bug that stopped
  the entry point from calling anything, and a cheat-key table that had
  drifted out of step with the instructions screen.

**Where it was not used**

- The division of work and the project schedule.
- The gameplay rules in `game.py`, `level.py` and `entities/`, which we
  designed and wrote.
- The visual direction.

**How we worked with it**

We treated its output as a proposal, not as an answer: everything was read
line by line, tested, and changed where we disagreed. Several of its
suggestions were rejected — a merged cheat-key table that crossed the
boundary between our two modules was left as recorded technical debt
instead, because the cost of touching a teammate's file outweighed the
benefit.

## Known limitations
- `pacgum` is validated but not applied: every walkable cell receives a
  pacgum.
- Cheat keys are the digits 1 to 5; on AZERTY keyboards they need Shift.
- Maze size has no agreed ceiling: above about 50×50 the maze is legible
  but taller than most screens.
- The renderer copies the pickup sets every frame; fine at the default
  sizes, wasteful on very large mazes.
- Ghost sprites are 32×32 and scaled up.
- There is no sound: `pygame.mixer` has no MLX counterpart.
